## Why this test is necessary

`WorldPlayerPersistence.write` catches exceptions from real file-backed `FilePlayerRepository.saveForWorld` and completes the `SaveTicket` exceptionally while incrementing failedCount. `LocalSession.saveAccountFinal` waits for at most five seconds and catches/logs `V5123_ACCOUNT_FINAL_SAVE_WAIT_FAILED`, but session teardown continues and removes the player. The previously healthy account file may remain *available* to `loadForWorldSession` for a fresh process/World. If a final-session mutation was not saved, a later successful login may silently start from OLD state. This is not a full recovery specification; it is a demonstrated gap to be closed by a separately designed durable, fail-closed intent/commit protocol.

## Deterministic authentic TCP + file evidence

New regression `G21177CoreSocketFailedFinalSaveStaleReconnectIntegrationTest` uses real loopback `Socket`/`ServerSocket` and actual `LocalSession` against three independently created/closed Worlds. Phase A: first login to a normal named profile, World-owned command writes `extension.core_final_failure.phase=PREVIOUS_DURABLE`, real final logout saves the file. Phase B: new World with real `FilePlayerRepository` and **existing test-only beforeWorldReplace seam** logs in and hydrates OLD, World-owned command writes `NEW_UNSAVED`, test arms an `IOException` before actual account replacement during final save. Assert explicit injection fired, persistence worker failedCount increased, old file bytes byte-for-byte unchanged, player unregistered and World fully shut down. Phase C: another fresh World with normal file repository accepts valid TCP login from the same named account and currently hydrates OLD, not the uncommitted NEW, demonstrating **staleReconnectCurrentlyAllowed=true** and **durableFailureQuarantineImplemented=false**. No secondary profile, no leaked JVM locks or temp files.
