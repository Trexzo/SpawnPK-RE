# G21.226 — NOFOLLOW all ancestors of the cooperating OS session lock path

G21.185's OS session lock `LocalCrossJvmAccountSessionLock.acquire` checks `Files.isSymbolicLink(parent)` only on the *immediate* parent. A symlinked grandparent can still redirect the account's stable `.session.lck` path to another directory, undermining confidence in exact-path writer scope. This does NOT by itself establish a second owner exploit or a durable epoch violation, but it is a concrete source gap.

G21.226 traverses the normalized account parent up to filesystem root, refusing symlinked or non-directory existing components with NOFOLLOW before `Files.createDirectories` and repeating the check immediately afterward. The existing G21.185 stable lock file and G21.221 optional fileKey diagnostic remain otherwise unchanged; no lock unlink/rename/cleanup, no replay/grant or login changes. The new test acquires a REAL OS lock for an ordinary nested account, then on Unix constructs a symlinked grandparent pointing to that actual directory. It proves both grandparent and direct symlink parent are rejected before either target lock file can be created. Windows reports symlink-creation support explicitly rather than claiming a missing test succeeded.

**Limit:** path checks do NOT give atomic protection against a concurrent hostile path swap after preflight, inode replacement, hard links, mount aliases or uncooperative external writers. No authenticated durable owner generation, final-save ACK or safe process-crash recovery/ACTIVE retirement.
