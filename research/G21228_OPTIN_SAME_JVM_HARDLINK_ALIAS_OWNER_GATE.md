# G21.228 — opt-in observed fileKey alias exclusion during JVM session admission

Certified ancestor: existing G21.218 session pending + G21.216 RAW lock, with current G21.227 [Draft #2703](https://github.com/Trexzo/SpawnPK-RE/pull/2703) demonstrating a real same-inode TWO-WORLD admission under two hard-link path aliases. G21.227 negative has **555 focused registered** and remains the exact opt-out proof. This change is strictly default OFF.

G21.228 adds `spk.local.experimentalRejectSameJvmAccountInodeAlias=true`. On opt-in account-session acquire, read the existing account file's non-null `BasicFileAttributes.fileKey` with NOFOLLOW and regular-file requirement OUTSIDE the JVM-wide account monitor. Missing bootstrap file has no inode key yet, is allowed but gives no guarantee. Under the monitor deny an admission when its existing fileKey equals another live Token's initial inode witness OR another pending admission's fileKey, even if normalized path strings differ. Keep pending fileKey until OS process lock has been acquired and Token committed or until failure cleanup (which must release OS lock first). Reobserve account file identity outside the monitor just before committing Token; if file object changed, refuse. No filesystem calls while holding the JVM-wide lease monitor.

The deterministic regression makes true hard-linked account paths A/B plus unrelated path C. With all existing session/RAW/OS flags AND G21.228 property ON, pause original A after its per-path pending claim via existing TEST-only G21.218 probe: B's same-inode alias is denied before trying its sibling OS lock, while C's distinct inode obtains a genuine OS lock. Resume A to a real bound WorldPlayer generation, then prove B remains denied when A's Token is live, with no second alias lock leaf created. Unrelated C owner remains accepted. G21.227 historical parent still runs with alias gate OFF and demonstrates the gap.

**HARD LIMITS:** Observed fileKey is a JVM-local best-effort alias witness, NOT a stable durable owner epoch. Atomic account replace changes the inode, and a new alias created after original registration may not share the token's initial key. Missing first-login/bootstrap file has no inode witness. RAW writers and stand-alone strict writers are not fully covered by this session-only alias guard. Cross-JVM aliases remain independent because account lock names differ, and malicious hardlink/object/path races, inode reuse/ABA, process death, LIVE property toggles and uncooperative external writers remain outside the protocol. No ACTIVE marker retirement, safe relog, grant or replay.
