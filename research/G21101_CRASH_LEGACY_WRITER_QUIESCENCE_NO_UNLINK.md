# G21.101 — real crash and legacy-writer limits for lifecycle quiescence

Parent certified G21.100 `254dded0822c44ce6bd2360ce3d068c827dc0f4c`, [Actions #38068591602](https://github.com/Trexzo/SpawnPK-RE/actions/runs/38068591602) SUCCESS (400 Java 11 focused). Issue #2381.

**G21.100's positive scope is only a coordinating lock lease:** the current strict account, PREPARED journal and COMMIT writers hold an account-qualified stable JVM+OS lifecycle lock from before creation of temp files through publication and cleanup. A death frees that **volatile OS lock**, not the orphan itself. G21.101 exercises *three actual hard JVM terminations inside real production hooks*: strict terminal `BEFORE_ATOMIC_REPLACE`, PREPARED journal `BEFORE_LINK`, and COMMIT `BEFORE_LINK`. Three separate OS JVMs each restart, reacquire the actual lifecycle+publication locks and perform the bounded G21.99 temp audit. All three abandoned temps stay intact, unlinked and **not safe to delete**, with expected canonical negative states, no repaired account, no grant and no detached recovery. Unique `Runtime.halt(121..123)` codes and child-emitted markers are required; child process timeouts are bounded.

**Prior-version / nonparticipating-writer counterexample:** a new independent JVM deliberately acts as a *legacy-style* strict publisher, never acquiring the G21.100 lifecycle domain. It creates and forces a real strict temp containing byte-for-byte copies of an existing valid canonical account, forges its mtime 60 days old, then blocks before publication. While that process is demonstrably alive, G21.100 `inspect` **succeeds** because no participating writer holds its lifecycle lock; it sees the temp but grants no disposal permission. On release the old-style publisher successfully acquires only G21.39's account publication lock and atomically replaces the canonical account. Canonical bytes stay equal, but the physical file key changes, definitively demonstrating that an older/untracked publisher can still complete after apparently quiet G21.100 inspection.

**Explicit reporting:** `MailboxPublicationWriterLifecycle.Report` now documents `crashEpochDurabilityVerified=false`, `historicalWriterParticipationVerified=false`, `legacyWriterCanStillPublish=true` and `orphanTempDisposalSafe=false`, in addition to existing `unlinkAuthorized=false`, `allWriterGenerationsCovered=false`, `uncooperativeWritersExcluded=false`, and all reward, replay, session and ACK denial flags.

**Limits:** The legacy-style test models prior-version publication semantics; it is **not** a proof that every historical binary behaves that way, and JVM `Runtime.halt` is not a true machine-power loss. Neither an expired OS lock nor a reported clean lifetime is durable all-generation quiescence; this milestone cannot authorize temp unlink, garbage collection, promotion or any item settlement.
