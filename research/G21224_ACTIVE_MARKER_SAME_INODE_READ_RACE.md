# G21.224 — in-place ACTIVE sidecar mutation during a bounded read

The G21.222 reader bounds 4096 bytes, NOFOLLOW and before/after fileKey, while G21.223 checks strict four-field account-bound format. Neither before/after inode alone detects an **in-place write to the same file object** between the bounded read and final diagnostic interpretation. This is not a known account-admission exploit, because marker existence continues to deny login; it is a diagnostic stability/fail-closed issue.

G21.224 adds bounded length agreement `after.size==initial.size==bytesRead` and file last-modified equality in the post-read check. A deterministic test-only callback between the real bounded file read and final attribute capture appends to the same marker inode; a second case rewrites equal-size bytes and explicitly advances mtime. Both must return `G21.224 REVIEW_MARKER_MUTATED_DURING_READ_NEGATIVE`, with marker existence still denying admission and no marker delete. Restore valid forced G21.188 marker to prove normal negative diagnostic behavior. This cannot defeat a malicious writer capable of restoring the file metadata, swap-after-check, or concurrent external writes. It is **not** a digital signature, durable ownership epoch, automatic recovery protocol or safe ACTIVE retirement.
