## Security question

G21.144–156 have robust *retained in-memory shape*, portable self-hash and decoded physical-byte consistency checks; these are all made by **one caller retaining both snapshots**. None constitutes a trusted original historical custody chain, an independently enrolled writer, a trustworthy key registry, an atomic crash-safe epoch, or a fence against raw/default/old/future writers. An observer can generate a new coherent report.

G21.157 adds **only a cryptographic verification building block**: `MailboxDetachedHistoricalCandidateSignatureV1`. It accepts an existing G21.129 historical report, a bounded canonical account identifier, a caller-supplied X.509 SPKI EC public key, caller-supplied lowercase SHA-256 fingerprint of the key's encoded form, and a caller-supplied detached SHA256withECDSA DER signature. Java 11/JCA P-256 is the sole accepted EC key type. It first invokes the complete inherited G21.156 retained-report preflight (`compare(historical,historical)`) and requires exact observational MATCH with no fileKey uncertainty. Then it deterministically creates a domain-separated message from the account name and SHA-256 of a sorted, bounded binary snapshot of *both historical BEFORE and AFTER*: portable v1/v2/v3 bytes and digests, physical account/journal/commit SHA/size/created/modified, and sorted evidence-leaf names plus physical SHA/size/timestamps.

The opaque filesystem `fileKey` is **not serializable as a portable stable cross-process identity** and is deliberately NOT part of the digest. Existing preflight must observe a non-null source key; the candidate signature DOES NOT authenticate the original inode/fileKey. This method does no disk read, lock, rescan, or writer enrollment; no signing code runs in production. The only output status is `VALID_SIGNATURE_UNTRUSTED_KEY_NO_AUTHORITY`, with **every** authentication, writer-exclusion, epoch, cleanup, grant/replay/session/release/ACK property permanently false. The API never returns a grant or an authenticated-source token.

## Threat model and acceptance limitations

**Checking a signature with a public key DOES NOT certify who controls that key.** Because this method receives both candidate public key and expected fingerprint from the same caller, a forger may create their own keypair and matching fingerprint and sign coherent invented data. It will pass the mathematical signature check. This deliberately remains a *no-authority* result. Real independent historical provenance would require out-of-band authenticated provisioning, capture-time archival of custody evidence and a replay-safe trust/rotation model, none of which exists in this branch. The signature also cannot reconstruct excluded legacy/uncooperative writers or an atomic cross-file durability epoch.

**Strict negative gates:** absent/invalid account, missing/uncertain historical source, a mismatched v3 account context, a missing/wrong candidate key fingerprint, malformed key/sig bounds, unsupported EC curve, or cryptographically invalid signature result in checked IOException `CANDIDATE_SIGNATURE_UNSAFE_NO_AUTHORITY` with diagnostic reason. Candidate status must **not** be treated as an independent pin or a replay/reward settlement authorization.
