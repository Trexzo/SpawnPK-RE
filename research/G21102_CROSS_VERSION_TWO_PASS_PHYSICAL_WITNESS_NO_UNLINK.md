# G21.102 — two-pass physical file evidence and cross-version writer limitations

Parent certified G21.101 `cfa5d537ac8c02e1ccd85d52ad6c77bc17c36f4a`, [GitHub Actions #38125155668](https://github.com/Trexzo/SpawnPK-RE/actions/runs/38125155668) SUCCESS, 401 Java11 focused; issue #2383.

G21.101 proved that a previous-version/uncooperative writer may publish AFTER an apparently quiescent G21.100 audit. G21.102 strengthens the *bounded forensic detection*, **not the writer fence**. The existing G21.99 audit now retains an immutable three-leaf canonical physical witness (account, PREPARED journal, COMMIT; exact path, present/absent, file identity, size, mtime). It is produced entirely under G21.99's bounded cooperating publication lock and only after canonical pre/post physical verification. Its existing account-scoped orphan candidate list already includes path, kind, disposition, file identity, size and mtime. No temp content is promoted.

New opt-in `MailboxCrossVersionPublicationEvidenceAudit.inspectTwice` resolves the account file exactly once and performs **two separate full G21.100 lifecycle → G21.99 publication-locked** observations, releasing BOTH locks in between. It compares all three canonical physical witnesses and every exact bounded candidate. Differences throw `G21.102 CROSS_VERSION_DISK_WITNESS_DRIFT_NO_UNLINK`. It has no deletion or session authority; even success declares `legacyWritersExcluded=false`, `futureWritersExcluded=false`, `allWriterGenerationsCovered=false`, `crashEpochPersistentlySealed=false`, `unlinkAuthorized=false`, `cleanupAuthorized=false`, and all reward, replay, release and client ACK flags false. The between-passes callback is a test seam, not a durable cleanup token.

**Real multi-JVM proof:** a legacy-style writer creates a 60-day-old valid strict temp without G21.100 participation; it atomically replaces canonical account bytes with byte-for-byte IDENTICAL bytes but a different physical file key *between* two bounded checks. Must reject the drift. Another legacy-style writer publishes after TWO perfectly consistent passes: the report stays negative-only and the canonical inode is subsequently replaced, proving that even matching witnesses don't exclude future old writers. Separately, a tracked G21.100 strict writer hard-`Runtime.halt(124)` exits before atomic move; a new fresh JVM re-acquires both cooperating domains, observes the orphan still physically present, and never cleans, repairs, grants or replays it. All canonical bytes unchanged, publication leases zero. Java 11 manifest 401→402; standalone `g21102MailboxCrossVersionTwoPassEvidenceRegression`.

**Boundary:** Unlike true intergenerational fencing, the two-pass inspection only detects observed physical changes within its finite temporal scope, and even two passing checks cannot guarantee future writers will not act. Filesystem object keys are diagnostic, not a disposal capability. JVM halt is not machine power loss. No COMMIT deletion, session restoration, reward settlement, auto-unlink, claim replay or ACK; G21.87–88 and frozen R25 #1847 remain unchanged. Stacked PR Draft/unmerged until exact-head CI.
