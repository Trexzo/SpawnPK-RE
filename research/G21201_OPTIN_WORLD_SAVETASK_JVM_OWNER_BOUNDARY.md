## New narrowly opt-in worker boundary

`LocalJvmAccountSessionLease.requireCapturedSaveOwnerIfLeased(exactAccountPath,snapshotAccount,owner,capturedGeneration)` resolves the currently held JVM lease by normalized exact file path (under existing active map), then checks token identity and captured player object, expected generation, and account name under Token→active lock order. If a currently held lease has a bound owner and the captured owner is foreign, the generation mismatches, or the snapshot account differs, the check throws `G21.201 CAPTURED_SAVE_OWNER_NOT_BOUND_TO_LEASE`. This is only **in-process object identity**; the lease can disappear when JVM dies and it does not authenticate raw file bytes.

The existing `WorldPlayerPersistence.SaveTask` carries immutable `owner` and `expectedGeneration` from captured World-owned SaveTask. In the existing FIFO worker, immediately before a normal/final `FilePlayerRepository.saveForWorld`, the code consults the current opt-in account lease using the repository's exact file resolver. If the lease is present, foreign captures are refused before repository I/O; if none is present, the previously unleased/default-OFF account write path remains unchanged. The writer's existing failure accounting/final-save World-lifetime negative still processes a thrown guard error. **Actual final-save worker executes AFTER World unregisters player**: comparison intentionally checks saved exact owner identity+captured generation, not `WorldPlayer.accepts(generation)` which is false after unregister.

**Hosted CI caught a G21.184 late-toggle compatibility regression in the first candidate**: a session that really entered World while the JVM lease option was OFF must not be mistaken for a later token acquired by a second same-account World after opt-in. The correction records an actual early, unleased WorldPlayer identity/path/generation using weak in-JVM provenance on `LocalSessionPlayerInitializer` registration. When an existing newer lease belongs to someone else, the ordinary/final SaveTask for that *previously admitted unleased* owner follows the historic unguarded path; an unrelated player with no prior admitted unleased provenance still fails the held-token check. The older G21.184 focused regression must remain green: it deliberately reproduces **two successful, stale-overwriting saves** and shows dynamic opt-in is not safe. This is NOT a fix for late flag toggling and NOT authenticated ownership. The weak provenance is memory-only, never a durable receipt or positive session authorization.

The new guard covers **SaveTask queued normal and final account saves only**, not `CheckpointDrainTask`'s separate `write` path or every mailbox/strict terminal, alternate PlayerRepository or raw writer. The current opt-in JVM owner token is not passed as a cryptographic or durable receipt to disk. Neither successful check nor a forced G21.199 account-content witness authorizes marker retirement, replay, settlement or positive recovery.

## Regression

It validates exact `WorldPlayer`/generation guard, manually submits a different `WorldPlayer` with same username/generation and a stale-generation/wrong snapshot account probe to the preflight (must all fail); establishes a counter boundary AFTER manual calls, modifies live World-owned extension and logs out normally, then proves the actual asynchronous final-save worker increased the guard counter after that boundary, forced final account mutation persisted, and healthy token released. A subsequent new World TCP login remains refused due to unchanged ACTIVE review sidecar. **Direct forged-owner probes invoke the same guard method, not arbitrary foreign asynchronous captures**; they do not independently prove injection of a forged SaveTask into production FIFO. Code and assertions must not claim a durable authenticated owner epoch.
