# G21.230 — opt-in bounded account hardlink count admission veto

G21.229 [Draft #2710](https://github.com/Trexzo/SpawnPK-RE/pull/2710) on G21.228/G18.8.8 cumulative documents two independent JVMs admitting different pathname hardlinks to the SAME account inode even with same-JVM fileKey alias gate on. The OS session lock path derives from the filename and thus differs per alias.

The experimental default-OFF `spk.local.experimentalAccountHardlinkCountGate` adds an admission-time NOFOLLOW regular-file check for existing account files. If `unix:nlink != 1`, reject before session lease/RAW reservation or OS lock acquisition. If the Unix attribute view is unavailable, **fail closed** when the flag is enabled rather than claiming protection. Missing account files are allowed (no inode exists yet) and default-OFF behavior is unchanged. This opt-in check is shared between cooperating `LocalJvmAccountSessionLease.acquire` and `reserveRawWrite` (FilePlayerRepository, named profile, primary AccountStore and standalone strict). Not an authenticated inode epoch: link count can change after check, an uncooperative writer can ignore it, and platform support is a deployment preflight requirement.

The new test creates real hardlinks and an independent one-link control. Both parent and child Java processes independently attempt normal session and RAW writes via the SAME tested policy; both must refuse alias and allocate NO OS lock leaf, while an unrelated one-link account can acquire and release both reservations. This is a **cooperating admission hardlink veto**, not durable cross-process file identity or safe crash recovery. `562` focused, hosted Java11 major55 and full Gradle required. Draft/unmerged, default OFF. Original SpawnPK behavior, LIVE flag toggles and ACTIVE review marker retirement unchanged.
