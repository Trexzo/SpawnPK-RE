## Newly closed semantic transports

### C2S4 — public chat message

Exact `rs.Client.C()` input handling:

- parses colour prefixes such as `green:`, `cyan:`, `purple:`, `white:`,
  `flash1:`, `flash2:`, `flash3:`, `glow1:`, `glow2:`, `glow3:`;
- parses effect prefixes `wave:`, `wave2:`, `shake:`, `scroll:`, `slide:`;
- emits C2S4;
- reserves a variable-byte length;
- writes effect and colour through `rs.x.e.m(int)` (128-value byte transform);
- compresses the remaining message through `rs.P.a(String, rs.x.e)`;
- patches the encoded body length.

Authority: `EXACT_CURRENT_CLIENT`.

Server moderation/filter/rate-limit policy remains `UNKNOWN_SERVER_AUTHORITY`.

### C2S60 — generic name-entry response

Exact `rs.Client` input path pairs the server-opened name prompt with:

```
"Enter name:"
 -> local input mode
 -> C2S60
 -> rs.O.a(String) name key
 -> i64
```

The analogous amount prompt:

```
"Enter amount:"
```

uses the already-known C2S208 integer amount transport.

Therefore C2S60 is the exact name-entry response transport, not an unknown
fixed-8 packet.

Authority: `EXACT_CURRENT_CLIENT`.

The server-side meaning of the particular prompt remains owned by the interface
or content flow that opened it.

### C2S95 — chat-mode settings

Exact `rs.Client` chat-control paths snapshot three mode fields, update them
from the chat-control menu, then emit:

```
C2S95
byte gu
byte cE
byte fZ
```

The same packet is emitted when private-message activity changes the relevant
chat visibility state.

Authority: `EXACT_CURRENT_CLIENT`.

Historical 317 clients use the same three-byte family for public/private/trade
chat modes; the v308 classification here does not depend on that history for
framing, only for naming corroboration.

### C2S126 — private message

Exact `rs.Client.C()` path when the private-message input mode is active:

- requires non-empty entered text;
- emits C2S126 variable-byte packet;
- writes recipient name key `le` as i64;
- compresses the entered message with `rs.P.a(String, rs.x.e)`;
- patches the variable-byte body length;
- locally normalizes/echoes the resulting private message presentation.

Authority: `EXACT_CURRENT_CLIENT`.

### C2S218 — report-abuse submission

Exact `rs.Client.c(rs.n.e)` handles content types `601..612` as the report
rule choices and `613` as the local toggle used by the report UI.

Submission emits:

```
C2S218
i64 rs.O.a(kr)       // entered player name key
u8  (contentType-601)
u8  nz ? 1 : 0
```

Authority: `EXACT_CURRENT_CLIENT`.

Server-side report retention/moderation policy is `UNKNOWN_SERVER_AUTHORITY`.

## Client control / telemetry families

These packets are exact-current client behavior but do not represent separate
gameplay intents. They are generated by UI/camera/control state or legacy
interaction counters.

### C2S85

Interaction counter threshold probe:

```
counter ny increments conditionally
ny >= 53
 -> C2S85
 -> u8 66
 -> ny = 0
```

The ordinary semantic interaction follows separately in C2S18.

### C2S86

Camera/orientation control update from `rs.Client.bz()`.

When the client has detected camera-key state and its throttle reaches zero:

```
C2S86
rs.x.e.d(fs)   // 16-bit BE
rs.x.e.o(ft)   // 16-bit BE with +128 low-byte transform
```

This is client control state, not a gameplay action.

### C2S120

Tab-state acknowledgement.

Exact v308 behavior:

- a pending tab-state marker `er` makes the tab area dirty;
- when `er == fL` (the active tab), the client clears `er`;
- emits C2S120 with the one-byte active tab id `fL`.

Historical 317 source independently identifies the corresponding state as the
flashing sidebar-tab acknowledgement. That historical naming is corroboration;
the v308 send condition/payload above are exact-current proof.

### C2S136

Empty interaction-counter probe.

A counter accumulates target/player interaction values and, once it reaches the
threshold, emits empty C2S136 and resets. The real semantic interaction packet
is emitted separately.

### C2S148

it resets the counter and emits empty C2S148.

### C2S150

### C2S246

Randomized integrity/control telemetry.

- `Math.random()` generated values;
- optional branches;
- a patched body length.

This is exact client control/telemetry behavior, not a domain action.

No server anti-abuse interpretation is claimed beyond the observed client-side
randomized control packet.

## Four serializer-only semantic unknowns

After the classifications above, only these four opcode meanings remain
unresolved:

```
2
6
78
109
```

Their exact serializers are:

### C2S2

```

```

### C2S6

`rs.o.a.a.a.p`

```
C2S6
u16_BE constructorArg
```

### C2S78

`rs.o.a.a.a.g`

```
C2S78
(no body)
```

### C2S109

`rs.o.a.a.a.x`

Constructor arguments are rearranged into six fields and serialized:

```
C2S109
arg1 -> rs.x.e.n(int)   // LE16
arg2 -> rs.x.e.o(int)   // BE16 with +128 low byte
arg3 -> rs.x.e.d(int)   // BE16
arg4 -> rs.x.e.o(int)
arg5 -> rs.x.e.p(int)   // LE16 with +128 low byte
arg6 -> rs.x.e.d(int)
```

### Important negative finding

A whole-JAR binary constant-pool scan of all 10,472 classes found no other class
directly referencing any of these four concrete serializer classes by internal
class name. Each concrete class name occurs only in its own classfile.

`rs.Client` exposes the generic extension seam:

```
public void a(rs.o.a.a.a packet)
 -> packet.a(fv)
```

but no class in the supplied JAR calls that generic method either.

Therefore exact v308 proves:

- the four serializers exist;
- their byte contracts are exact;
- they are not statically invoked by the supplied client's own code.

Reflective/dynamic/external construction remains possible.

Their original server/application meanings remain
`UNKNOWN_SERVER_AUTHORITY` and must not be guessed from opcode number or
packet shape.
