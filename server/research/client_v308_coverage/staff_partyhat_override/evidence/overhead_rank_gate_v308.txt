2. aC IS SERVER-PUBLISHED PLAYER STATE

Exact rs.a.k.a(rs.x.e) appearance parser begins:

aY = y()    // u8
bd = y()    // u8
bf = y()    // u8
bg = y()    // u8
bh = y()    // u8
aC = B()    // signed big-endian 16-bit
then br[12] appearance entries

rs.x.e.B() is signed BE16:
    value = ((byte0 & 255) << 8) + (byte1 & 255)
    if value > 32767: value -= 65536

The rs.a.k class has one direct aC write: this appearance parser.
rs.Client also updates player.aC while decoding the public-chat player mask,
so aC is client-visible privilege/rank-like player state rather than an item id.

3. rs.l.h.b(int) IS AN ICON INDEX REMAP/ANIMATION LOOKUP

Exact behavior:

if (rs.l.j.b contains key)
    return ((rs.l.a.a)rs.l.j.b.get(key)).b()
return key

The exact v308 static table contains animated/remapped keys including:
21, 32, 45, 291, 333, 340, 344, 348, 352, 356.

Therefore constants 0, 19 and 31 are identity lookups in the static table,
while aC values can optionally resolve through the native mapping table.

4. STRUCTURAL SEPARATION FROM bs OVERRIDE

The overhead badge branch reads:
    player.br[0]   ordinary HEAD appearance component
    player.aC      privilege/rank-like state

It does not read:
    player.bs      optional extra wearable-model appearance item

Therefore:
- wearing a staff partyhat can activate the native fE[] badge branch;
- publishing that partyhat only through bs does not satisfy the HEAD gate;
- bs remains the separate 13th wearable-model channel proven in the sibling
  exact_client_bs_and_c2s16.txt evidence.

5. CURRENT LOCALLAB GAP

Current main BootstrapPackets.appearanceBlock(...) serializes:

    putU16(b, 0); // signed-short role aC; zero is safe in the parser

So LocalLab currently has the exact wire position but no semantic rank/privilege
state feeding aC. That is a server/domain implementation gap, not a client
research gap.
