1. GENERIC CONTINUE WIDGET PATH

Exact rs.Client menu construction:

if widget.M == 6 and click is inside widget bounds:
    menu action = 679
    menu parameter eG = widget.aw

Exact menu dispatch:

if menuAction == 679 and !eZ:
    write opcode 40
    write widget id with rs.x.e.d(int)
    eZ = true

rs.x.e.d(int) is unsigned big-endian 16-bit serialization:

    byte0 = value >> 8
    byte1 = value

Therefore:

    action-6 Continue widget
        -> menu action 679
        -> C2S40(widgetId:u16_be)

2. GENERIC ORDINARY BUTTON / OPTION PATH

Exact rs.Client menu construction:

if widget.M == 1 and local controller gating accepts it:
    menu action = 315
    menu parameter eG = widget.aw

Exact menu dispatch action 315 eventually writes:

    opcode 185
    widget id via rs.x.e.d(int)

Therefore:

    ordinary action-1 widget
        -> menu action 315
        -> C2S185(widgetId:u16_be)

This is the exact generic button transport used by many client interfaces.
The semantic meaning of a widget still comes from its interface/controller
context; C2S185 itself is not intrinsically a dialogue-option packet.

3. STANDARD OPTION ROOT HOTKEY SET

Exact rs.Client static array jy:

    2459
    2469
    2480
    2492
    14170

Exact rs.Client.keyPressed behavior:

if current chatbox/root field gp equals one of jy[]:
    top-row key codes 49..53 (1..5):
        ap = "::dialogueoption " + (keyCode - 48)

    numpad key codes 97..101 (NUMPAD1..NUMPAD5):
        ap = "::dialogueoption " + (keyCode - 96)

The normal outbound command drain later sees ap != null and writes:

    C2S103
    var-byte payload length = ap.length() - 1
    payload string = ap.substring(2)
    rs.x.e.a(String) appends newline byte 10

So exact keyboard option selection is:

    key 1..5 / numpad 1..5
        -> C2S103
        -> "dialogueoption N\n"

It does NOT synthesize C2S185 and does not need to know the individual option
widget id.

7. SERVER-AUTHORITY BOUNDARY

The client proves:
- transport;
- root families;
- local hotkey behavior;
- generic widget action classes.

It does NOT prove:
- which dialogue node the original server is in;
- which option text maps to which gameplay result;
- permission/fee/reward/state-transition rules;
- whether original server treated keyboard widget id 4907 specially or simply
  as a generic Continue signal.

Those remain server/content authority.

8. IMPORTANT IMPLEMENTATION CONSEQUENCE

A semantic dialogue layer should normalize at least three client input forms:

    DialogueContinue(widgetId)
      from C2S40 mouse action-6 Continue

    DialogueContinue(4907)
      from exact Space hotkey

    DialogueOption(index)
      from C2S103 "dialogueoption N"

and, where a concrete option widget is proven:

    DialogueOption/WidgetAction(widgetId)
      from C2S185 ordinary action-1 widget

Raw opcode/widget identity should remain transport/presentation evidence rather
than become public gameplay API identity.
