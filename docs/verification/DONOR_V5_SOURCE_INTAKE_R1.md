## Source-local inventory ABA and publication bypass hardening

A slot-for-slot comparison is insufficient if inventory A is mutated to B and then restored to A before a prepared request is published. The existing BankState now tracks a **source-local monotonic inventory mutation revision**, advanced by normal inventory postimage replacement (`replaceStacks(inventory, ...)`), semantic full replacement, exact-slot semantic consume and account snapshot restore. A prepared recipe seals this revision along with the existing bank-overlay view revision. Ordinary changed-slot denial retains `RECIPE_STALE_INVENTORY_POSTIMAGE`; only restored-value ABA is reported as `RECIPE_STALE_INVENTORY_GENERATION`.

The source-only regressions exercise semantic replace-and-restore, exact-slot consume-and-restore, account snapshot restore, and structural add-and-restore. The mixed-item BankState integration regression additionally tests queue-full backpressure, a same-values semantic inventory replacement, rejection of the old prepared request with zero queued recipe bytes, and successful publication from a fresh prepared request. Rejected inventory packet publication and invalid semantic postimages must leave the mutation revision unchanged; new accepted structural inventory publication advances it. A newly prepared request after a local mutation remains valid.

A prepared request that has begun a queue-backed publication attempt is permanently pinned to its outbound writer. It **may not subsequently invoke the direct source-only semantic-commit seam** to bypass backpressure or a failed publication. The successful queue-admission branch uses a separate internal commit path and the retry path remains available only through the original writer. The direct path is still intended solely for isolated source tests, not live gameplay authority. The read-only prepared preview now synchronizes on the same BankState monitor as preparation and queue publication.

**Boundary:** These revisions only fence calls participating in the same BankState instance and its tracked mutation APIs. This PR does not seal external mutable Stack aliases, implement a globally exclusive World/account lease, persist a revision over restart, provide crash-durable intent records, or prove original-client network acknowledgement. Do not claim an account-durability fix or enable donor recipes based on these local guards. Exact-head CI is mandatory.

Previously those paths could queue redundant container packets and increment bank/inventory mutation generations, with bank item/tab routes propagating a save request. `LocalSessionUiActionHandler` also unconditionally requested a save for deposit-all and placeholder widget actions even while the bank was closed.

R27 makes `BankState.applyDrag` refuse empty-source drags and return existing non-saving `*_DRAG_NOOP` statuses when the full postimage equals the source; `applyCommand` returns non-saving `SETBANKTAB_NOOP` / `SWAPBANKTAB_NOOP` for genuine semantic no-ops; and `depositInventory` returns `DEPOSITED_ALL_NOOP movedQty=0` without publishing or changing generations if no items move. The widget-level save bridge now requests `BANK_DEPOSIT_INVENTORY` only when the authoritative inventory generation advanced, and `BANK_PLACEHOLDERS` only when the canonical bank generation advanced. Actual completed drags, tab edits, deposit-all (including nonzero partials) and placeholder toggles remain unchanged and produce their normal save-intent signals.

Mandatory `bankNoopSaveAndLineageRegression` tests absent/empty drag sources and no backwards item theft, identical-stack swap, changed inventory and bank drag, repeat/empty bank tabs, same-source/target tab, closed/empty/repeat deposit-all, successful deposit of exactly five coins, and toggling placeholder metadata. It asserts no-op paths preserve packet byte count and mutation generations, while successful operations still emit packets and advance the relevant generation. This is source-only bank semantics; not an original-v308 GUI receipt, durable save acknowledgement, or evidence of cross-World account exclusivity. R26 Linux and Windows both passed before R27.

### R28 bank widget-to-session save bridge regression (new exact-head CI required)

R27 corrected no-op semantics inside `BankState` and gated `LocalSessionUiActionHandler` save calls by observed canonical inventory/bank mutation generation. R28 adds the **missing end-to-end source-level regression over the actual `handleWidget` action route**, not merely direct `BankState.apply*` return strings. The new mandatory `bankUiMutationSaveBridgeRegression` builds a real `LocalSessionUiActionHandler` and normal local player wiring with a counting `SessionBridge.saveAccount` callback and encoded packet writer. It tests closed-bank deposit/placeholder clicks, open empty deposit, a real placeholder toggle saving exactly once, a real five-coin inventory deposit saving exactly once and preserving coin counts, repeated empty deposit, and both widgets again after bank close. Every no-op must preserve packet-byte count, both semantic generations and callback count. This is only a source-level bridge callback proof, **not proof that an account snapshot was crash-durably committed or acknowledged by the original v308 client**. ### R29 World persistence snapshot identity fence before account-file routing (exact-head CI required)

The World-owned `WorldPlayerPersistence.captureDeferredSave` and `captureDeferredFinalSave` already require a current exact player/generation. But they previously accepted an arbitrary `username` argument for `PlayerSnapshotCodec.capture` and `captureOwnerLeaseWitness`. This lets a caller with genuine mutation authority over account A construct a snapshot *named and eventually filed* as account B, especially with experimental account leases disabled. It is a different boundary from R19–R28 bank-item save-intent checks, and should not be mistaken for overall crash-durable ownership.

R29 requires the requested snapshot account's **canonical registry identity** (trimmed, case-insensitive, Locale.ROOT, matching `PlayerRegistry` and `LocalAccountProfiles`) to equal the current registered `WorldPlayer.username()` while holding the player's existing mutation lock, after validating World generation ownership but **before** snapshot creation, final-checkpoint suppression, sequence allocation, lease witness capture, or enqueue. An unknown, null, blank, unrelated, or otherwise mismatched profile fails closed with `ACCOUNT_CAPTURE_PROFILE_OWNER_MISMATCH`. Legitimate differently-cased aliases of the *same* canonical account remain permitted. No change to save queue scheduling or file durability is implied.

The new mandatory `worldAccountCaptureProfileOwnershipRegression` exercises ordinary and final capture misrouting in both directions between two registered players, attempts for `opensrc`/null/blank alternate identities, a valid differently-cased canonical save and separate valid second-profile save, sequence numbering that must skip rejected captures, and exactly two correct repository writes. The existing World lifecycle/persistence integration tests remain mandatory. This is **source-local snapshot identity**, not a cross-JVM authenticated file-object epoch, durable write fencing, or original v308 client run. R27 and R28 passed exact-head Linux and Windows before R29; R29 must pass its own checks.
